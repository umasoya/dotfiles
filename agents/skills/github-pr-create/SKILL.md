# GitHub PRの作成

ユーザーが指定した変更を、レビューできるPull RequestとしてGitHubに作成する。本文案だけの依頼なら公開せず、案を返す。説明とPR本文はリポジトリの規約またはユーザーの言語に合わせる。

## 対象を確定する

- 適用されるAGENTS.md、CONTRIBUTING、PRテンプレートを読む。
- 作業状態、現在のブランチ、remote、upstream、コミット履歴と差分を確認する。認証情報入りのremote URLは出力しない。
- baseはユーザー指定や作業の文脈を優先し、指定がなければGitHubの既定ブランチを確認する。`main`を決め打ちしない。forkではPRの宛先とpush先を区別する。
- `base...head`のコミット済み差分と未コミット差分を確認する。無関係な既存コミットが混ざる場合は公開前に解消する。履歴の書き換えが必要なら確認する。
- 変更が複数の作業にまたがり対象を特定できなければ、対象だけ質問する。ユーザーの変更を破棄・上書きしない。

## レビューできる状態にする

- 依頼に必要な変更を完成させ、リポジトリ指定の検証と変更に適したチェックを行う。未実行や失敗は理由を記録し、成功したと書かない。修正は依頼範囲内で行う。
- PR作成の依頼には対象変更に必要なブランチ作成、コミット、通常のpushを含める。既にある承認を取り直さず、適用される実行権限に従う。既定ブランチ上なら作業ブランチを作る。
- ステージするファイルは明示し、ステージ済み差分も確認する。無関係な既存のステージ内容を混ぜない。認証情報、履歴、マシン固有設定を含めない。
- force push、既存コミットの書き換え、マージ、リリースは通常のPR作成に含めない。push拒否時は原因を調べ、履歴を書き換える前に止まる。

## GitHubに作成する

GitHub CLI (`gh`) または利用可能なGitHubツールを使う。CLIのオプションが不明なら実際の `--help` を確認する。認証や追加権限が必要なら秘密情報を求めず、必要な操作を説明する。

1. 宛先リポジトリ・base・headが一致する既存PRを確認する。同じ作業のPRがあれば重複作成せずURLを返す。既存PRの編集は依頼範囲に応じて行う。
2. タイトルは変更の結果を具体的に示す。本文はテンプレートを尊重し、問題・変更後の動作・実際の検証結果・残る制約を必要な分だけ書く。会話の経緯や放棄した案を持ち込まない。Issueの自動クローズは関係と完了を確認できる場合だけ指定する。
3. 対象ブランチを通常のpushで公開し、リポジトリ、base、headを明示してPRを作る。draft指定があれば従う。必須検証の失敗や未完了が残る場合はdraftにして理由を伝える。reviewer、label、milestoneは依頼や規約に根拠がある場合だけ設定する。
4. CLIで複数行の本文を渡すなら一時ファイルへ実際の改行を含む本文を書き、`--body-file`を使う。本文をシェルコードへ埋め込まない。構造化されたツールなら本文引数へ直接渡す。
5. 作成要求がタイムアウトした場合は同じbase・headのPRを照会してから再試行する。結果を確認できないまま作成要求を繰り返さず、状況を報告する。
6. 作成後にURL、base、head、draft状態を読み戻し、意図したPRであることを確認する。

最後にPRのURL、変更内容と検証結果を簡潔に報告する。CIが未完了ならローカル検証と区別する。作成できなければ完成済みの内容と残る障害を明示する。
